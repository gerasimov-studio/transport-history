# Правила работы с Transport History

Этот файл — общий контекст для всех чатов, работающих с репозиторием. Перед
изменениями прочитайте `docs/PROJECT_CONTEXT.md`, `ARCHITECTURE.md` и документ
нужного домена из `docs/domains/`.

## Границы проекта

- Мы разрабатываем систему, через которую пользователи создают и публикуют
  историю транспорта. Транспортные данные и демонстрационные наборы не
  изменяются, если задача прямо не просит работать с ними.
- Карта общемировая. Город не является контейнером данных или обязательной
  частью API: чтение ограничивается viewport, датой, масштабом и workspace.
- Основная карта модерируется. Личные сценарии и альтернативные истории живут
  в отдельных workspace и не попадают в основную карту без публикации.

## Архитектурные инварианты

- Один монорепозиторий, один React/Vite SPA и один модульный Go API.
- Браузер работает только со стабильным контрактом `/api`; PostgreSQL/PostGIS
  доступен только backend.
- Backend делится по доменам внутри сервиса. Новый микросервис появляется лишь
  при доказанной необходимости отдельного масштабирования, изоляции или цикла
  выпуска.
- Источник истины для изменений — журнал событий/changeset; публичная карта
  читает пространственные проекции.
- Все видимые пользователю строки должны проходить через масштабируемую i18n.
  Язык по умолчанию — английский; сейчас поддерживаются `en`, `sr`, `ru`.
- История загружается по области и времени. Тяжёлые выгрузки и перестроение
  проекций должны уходить в durable worker, а не блокировать HTTP.
- SPA остаётся лёгким: доменные страницы загружаются лениво, а стартовый граф
  history-route не превышает 200 KiB gzip.

## Домены и маршрутизация задач

- История и публичная карта: `docs/domains/history.md`.
- Редактор и commits/changesets: `docs/domains/editor.md`.
- Модерация и публикация: `docs/domains/moderation.md`.
- Пользователи, роли и эксплуатационное управление: `docs/domains/administration.md`.

Если изменение затрагивает несколько доменов, сначала зафиксируйте общий API и
инварианты, затем меняйте владельцев контракта. Не переносите бизнес-логику в
React ради удобства одного экрана.

## Проверки

Минимум перед завершением изменения:

```bash
npm run lint
npm run build
cd services/backend && go test ./... && go vet ./...
docker compose config
```

Запускайте релевантное подмножество во время разработки и полный набор перед
публикацией. `npm run build` также проверяет размер и состав стартового bundle.

Сохраняйте чужие незавершённые изменения в рабочем дереве. Не меняйте форму API
без одновременного обновления клиентов и тестов. При изменении архитектуры,
границ доменов или важных контрактов обновите соответствующий документ в
`docs/` в том же коммите.

Продакшен обновляется только в рамках явно согласованной публикации. После
развёртывания проверяются health endpoint и затронутый пользовательский поток.
